# Data directory

**Nothing in `data/raw/` or `data/processed/` is committed to git** (see
`.gitignore`). Medical imaging datasets are large and almost always carry
redistribution restrictions, even when they are publicly downloadable.

```
data/
├── raw/            <- YOU PUT THE DATASETS HERE (never modified by the code)
│   ├── xray/       <- chest X-ray images
│   └── mri/        <- brain MRI slices + tumour masks
├── processed/      <- generated by notebooks 01 and 04 (manifests with splits)
└── README.md       <- this file
```

The code never writes to `raw/`. Everything derived goes to `processed/` or
`outputs/`, so you can always delete those and regenerate.

## 1. Chest X-ray -> `data/raw/xray/`

Two layouts are supported. Set `data.layout` in `configs/xray_baseline.yaml`
**and** `configs/xray_transfer.yaml` to match (keep the two `data:` blocks
identical so the model comparison is fair).

### Layout A - `folders` (default; binary or multi-class)

One folder per class. An optional `train/` `test/` level is detected
automatically and used as the official split.

```
data/raw/xray/
├── train/
│   ├── NORMAL/
│   │   ├── IM-0001.jpeg
│   │   └── ...
│   └── PNEUMONIA/
│       ├── person1_bacteria_1.jpeg
│       └── ...
└── test/
    ├── NORMAL/
    └── PNEUMONIA/
```

Or without a split level:

```
data/raw/xray/
├── NORMAL/
└── PNEUMONIA/
```

Config:

```yaml
data:
  root: data/raw/xray
  layout: folders
  labels: [PNEUMONIA]                  # must match the folder names (case-insensitive)
  unlisted_folders_as_negative: true   # NORMAL/ becomes the negative class
```

`labels: [PNEUMONIA]` gives a binary task: **PNEUMONIA vs everything else**.

Images in folders *not* listed in `labels` (here, `NORMAL/`) are kept as the
**negative class** — an all-zero label row. That is what makes the binary task
work, and the loader prints how many images this affected and from which
folders.

Set `unlisted_folders_as_negative: false` only when those folders are a
different task rather than the negative class. Be careful: with a single label
and no negatives, the dataset becomes 100% positive, every metric becomes
degenerate, and training is meaningless. Notebook 01's class-distribution output
will show this immediately — check it.

For a **multi-class** task, list every class instead:

```yaml
labels: [NORMAL, PNEUMONIA, COVID]     # one sigmoid output per class
```

### Layout B - `csv` (required for multi-label)

A metadata file listing every image and its findings.

```
data/raw/xray/
├── labels.csv
└── images/
    ├── 00000001_000.png
    └── ...
```

`labels.csv` in either of these forms:

```csv
Image Index,Patient ID,Finding Labels
00000001_000.png,1,Cardiomegaly|Effusion
00000002_000.png,2,No Finding
```

or with one 0/1 column per finding:

```csv
image,patient_id,Cardiomegaly,Effusion,Pneumonia
images/00000001_000.png,1,1,1,0
```

Config:

```yaml
data:
  root: data/raw/xray
  layout: csv
  csv_path: data/raw/xray/labels.csv
  image_root: data/raw/xray/images     # what the CSV paths are relative to
  image_column: "Image Index"
  patient_column: "Patient ID"         # omit if the CSV has no patient column
  label_column: "Finding Labels"       # only needed for the separator-joined form
  label_separator: "|"
  labels: [Cardiomegaly, Effusion, Pneumonia]
```

If the CSV lists only file names while images live in sub-folders, the loader
searches for them - slower on first run, but it works.

### Patient IDs (important)

Patient-level splitting is what prevents the same person's images appearing in
both training and test. The ID is taken, in order of preference:

1. from `data.patient_column` (CSV layout);
2. from `data.patient_id_regex` — a regex with **one capturing group**, applied
   to the file name and then the full path:

   | file name pattern | regex |
   |---|---|
   | `00000013_005.png` (NIH ChestX-ray14) | `'^(\d+)_'` |
   | `patient00123_view1.jpeg` (CheXpert-like) | `'(patient\d+)'` |
   | `person1_bacteria_1.jpeg` (Kaggle pneumonia) | `'^(person\d+)'` |

3. otherwise from the parent folder name, or the file stem — meaning **one image
   = one patient**.

If no patient information exists, say so explicitly in the report: leakage
cannot be ruled out, and the metrics may be optimistic.

## 2. Brain MRI -> `data/raw/mri/`

### Layout A - `suffix` (default; e.g. the LGG / TCGA brain MRI dataset)

Images and masks in the same folder, masks distinguished by a suffix. The folder
name is used as the patient ID.

```
data/raw/mri/
├── TCGA_CS_4941_19960909/
│   ├── TCGA_CS_4941_19960909_1.tif
│   ├── TCGA_CS_4941_19960909_1_mask.tif
│   ├── TCGA_CS_4941_19960909_2.tif
│   ├── TCGA_CS_4941_19960909_2_mask.tif
│   └── ...
├── TCGA_CS_4942_19970222/
└── ...
```

Config:

```yaml
data:
  root: data/raw/mri
  layout: suffix
  mask_suffix: "_mask"
```

### Layout B - `parallel`

Two mirrored trees.

```
data/raw/mri/
├── images/
│   ├── patient001_slice12.png
│   └── ...
└── masks/
    ├── patient001_slice12.png     # or patient001_slice12_mask.png
    └── ...
```

Config:

```yaml
data:
  root: data/raw/mri
  layout: parallel
  image_dir: data/raw/mri/images
  mask_dir:  data/raw/mri/masks
  mask_suffix: ""                    # or "_mask" if mask names carry a suffix
  patient_id_regex: '(patient\d+)'   # needed: there are no per-patient folders here
```

### Mask requirements

- Same height and width as its image (checked automatically).
- Effectively binary. Values `{0, 255}` or `{0, 1}` both work — anything above
  127 (or above 0 for 0/1 masks) is treated as tumour.
- Slices with an entirely empty mask are fine and expected; they are kept and
  reported separately in the metrics.

Notebook 04 validates every pair and reports exactly what is wrong with any that
fail. **Run it before training.**

## 3. Volumetric formats (NIfTI / DICOM)

The pipeline expects 2D slices as ordinary image files. If your course dataset
ships as `.nii.gz` volumes or DICOM series, convert once to PNG/TIFF slices
before running notebook 04, keeping one folder per patient:

```
data/raw/mri/<patient_id>/<patient_id>_<slice_index>.png
data/raw/mri/<patient_id>/<patient_id>_<slice_index>_mask.png
```

That needs `nibabel` (NIfTI) or `pydicom` (DICOM), neither of which is in
`requirements.txt` — install only if you need them. Keep the conversion script in
the repository so the preprocessing stays reproducible, and document the
windowing/normalisation you applied.

## 4. `processed/` — generated, do not edit by hand

| file | created by | used by |
|---|---|---|
| `xray_manifest.csv` | notebook 01 | notebooks 02, 03 |
| `mri_pairs.csv` | notebook 04 | notebooks 05, 06 |

These freeze the train/val/test assignment, so training and evaluation can never
disagree about which images are in the test set. Delete them and re-run
notebook 01 / 04 to rebuild.

## 5. Licensing and ethics

Before using any dataset, check and record in your report:

- the licence and whether redistribution is permitted (usually it is **not** —
  which is why `data/` is git-ignored);
- how the data was de-identified;
- the required citation for the dataset;
- who annotated the labels or masks, and by what process.

Do not place identifiable patient data in this repository under any
circumstances. See `docs/ETHICS.md`.
